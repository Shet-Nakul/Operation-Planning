L1
Foundation
Organisation
The tenant root. Every table carries organization_id. No automatic cross-org isolation — controllers filter explicitly.
Organisation
organizations
idPK — used as organization_id FK everywhere.
nameDisplay name, e.g. "Central Hospital".
statusACTIVE default. No enforcement today.
Scheduling: Cron queries all orgs for GlobalSettings.schedule_date to decide whose run to trigger. Dirty-counter keyed by org_id in memory — dirty-triggered runs use today's date and remaining-days-in-current-month horizon; cron/manual runs target next full calendar month.
Planning: Auto-trigger and manual POST are per-org. Planning preparer iterates all departments under the org.
→ User 1:N → GlobalSettings 1:1 → Catalogs 1:N → Contract 1:N → Department 1:N
L2
Config Layer
Access & Configuration
System users, access roles (not clinical), and the single settings row per org that drives both solvers.
Role (system)
roles
namee.g. ADMIN, SUPERADMIN, VIEWER. Global — not per-org.
Distinct from clinical roles. This table controls API access. Clinical roles (e.g. "Senior Surgeon") live in the StaffTag catalog.
User → Role N:1
User
users
organization_idNullable — SUPERADMIN has no org.
role_idFK → Role. Governs API access level.
is_activeSoft disable. Inactive users cannot log in.
Usage: JWT issued on login. Every protected route requires a valid token. All mutations write to UserActivityLog.
Limitation: No per-org role — only one system-level role per user. Fine-grained department-level permissions do not exist.
GlobalSettings
global_settings
operation_hours_start/endBusiness window, e.g. 08:00/18:00.
surgery_planning_horizonPlanning look-ahead in days (default 3). Date window = horizon×2+1.
surgery_planning_resolutionSolver time-slot in minutes (default 15).
schedule_dateDay-of-month the scheduling cron auto-fires (1–31, clamps on short months).
Planning: horizon, resolution, operation_hours injected into every surgery planning payload.
Scheduling: schedule_date drives the 00:10 UTC daily cron.
Limitation: Single row per org — no per-department or per-season overrides. Mutating this triggers planning auto-run within 10 s.
Org → GlobalSettings 1:1
L3
Lookup Layer
Catalogs
Per-org lookup tables defining the vocabulary the system uses. All share the pattern: @@unique([org_id, name]), status ACTIVE, and CRUD under /api/catalogs/*.
StaffTag (clinical roles)
staff_tags
nameClinical role, e.g. "Senior Surgeon", "OR Nurse", "Operation Room", "ICU Bed".
colorUI hint only — not sent to solvers.
Scheduling: Pool's primary_role is a StaffTag name. Used in pool_role_map sent to scheduling solver.
Planning: Surgery stage role validated against this catalog (slug-insensitive). Sent as-is in surgery stage requirements. Non-staff resources (OR Room, ICU Bed) also modelled here.
Limitation: No FK from Staff.roles or surgery stages — referenced by name string scan in JS. Renaming a StaffTag does not cascade.
Staff.roles N:N (JSON) Surgery.stages[].role N:N (string)
Shift
shifts
name"Morning", "Night" etc.
aliasShort code: M, E, N. Used as the key in all solver payloads.
start_time / end_timeHH:mm window.
Scheduling: Demand matrix shift names converted to aliases → shift_requirements[pool][alias]. Staff weekly_template shift values validated and normalised against this. Rostering output uses aliases throughout.
Planning: shift_definitions block = all org shifts as alias → [[start,end]], plus hardcoded OH (operation hours) and F (full day).
Limitation: Staff pool-based weekly_template shift values silently normalised to "O" (off) if the value doesn't match any catalog alias — no validation error raised.
SurgeryStatusCatalog
surgery_status_catalog
nameStatus value, e.g. ESTIMATED, PLANNING.
to_planBoolean — if true, surgeries in this status are included in planning payloads.
Planning: Planning preparer queries to_plan=true entries. Empty table → default set {ESTIMATED, PLANNING, PLANNED}. Allows per-org customisation of which statuses trigger re-planning.
Limitation: No FK from Surgery.status — status values are not enforced to match this catalog. The catalog is advisory.
Specialization, Skill, ResourceType, OperationType, PhaseResource
Usage: Metadata catalogs stored on staff or matched by name on surgery. No FK from consumers — all referenced by name string. Usage checks scan JSON arrays in JS (never block delete for Specialization / OperationType / PhaseResource — usage check always returns empty).
Limitation: Not projected into any solver payload today. Renaming does not cascade to Staff or Surgery records.
L4
Constraint Layer
Forbidden Patterns & Contracts
Org-wide shift-sequence rules and per-staff employment contracts. Drive what the scheduling solver can and cannot assign.
ForbiddenPattern
forbidden_patterns
scopeGLOBAL — applies to all DYNAMIC contracts in the org.
forbidden_patternsJSON array of shift-alias sequences, e.g. ["N","M"] (night then morning).
Scheduling: One constraint object per pattern appended to every DYNAMIC contract's constraint array in the payload: { name, pattern, active:true, hard:true, weight }.
Limitation: Always hard constraints — no per-pattern soft/weight override today. Applies to all DYNAMIC staff regardless of role.
Org → ForbiddenPattern 1:N
Contract
contracts
typeSTATIC — fixed weekly template. DYNAMIC — solver-optimisable with constraints.
configurationJSON. DYNAMIC: schedulingRules + assignmentLimits. STATIC: unused.
Scheduling: DYNAMIC → constraint array in payload (schedulingRules + assignmentLimits + ForbiddenPatterns). STATIC → contracts[id] = null + staff gets a fixed weekly_template block. Groups with <2 DYNAMIC employees are skipped.
Limitation: Staff references Contract by the string contract_id — no FK. Deleting a contract does not update or alert the staff referencing it. Two parallel implementations: /api/contracts and /api/catalogs/contract — both live.
Org → Contract 1:N Contract → Staff 1:N (soft)
L5
Operational Pivot
Department
The grouping axis. Staff, HR pools, and surgeries all belong here. The planning solver builds one payload per department.
Department
departments
namee.g. "Cardiothoracic Surgery", "Trauma ICU".
statusACTIVE / INACTIVE.
Setting department_id on Staff/Pool/Surgery auto-derives and stores the string department via resolveDepartmentName(). Never set the string directly.
Planning: Preparer iterates departments and builds one payload per dept — pulling that dept's HR pools, eligible individual staff, and eligible surgeries.
Limitation: RenewableResourcePool has only a string department field — no FK to Department. Not included in per-dept planning grouping.
→ Staff 1:N → HR Pool 1:N → Surgery 1:N
L6
Workforce Layer
Staff
The employee record. Belongs to a department, linked to a contract, and assigned to one or more HR pools via a JSON array (not a FK). Clinical roles stored as a JSON array of StaffTag names.
Staff
staff
staff_idServer-generated: STAFF-<INITIALS>-####.
department_idFK → Department. String department auto-derived.
contract_idSoft string reference to Contract.contract_id — no DB FK.
rolesJSON array of StaffTag names — no FK.
role_distributionJSON: {"Senior Surgeon": 0.7, "Surgeon": 0.3}. Missing roles use 1/numRoles.
pool_assignmentsJSON: [{pool_id, pool_name}]. The link to HR pools — soft, no FK.
weekly_templateTwo shapes: pool-based {day:{pool,shift}} or role-based {day:[{start,end,role}]}.
Scheduling: DYNAMIC staff → employee_profiles with roles_distribution + pools. STATIC staff → additionally carry weekly_template. Union-find uses pool_assignments to group pools.
Planning: Pool-assigned staff contribute availability via Rostering output. No-pool STATIC staff whose primary role matches a surgery stage assigned token appear as individual resources with their weekly_template.
Limitations: pool_assignments has no FK — stale entries if a pool is deleted in DB. contract_id is a string reference — no FK. Role strings are not FK-validated. A single staff change triggers both scheduling AND planning auto-runs (within 10 s each).
Dept → Staff 1:N Contract → Staff 1:N (soft) Staff ↔ HR Pool N:N (JSON)
L7
Human Resource Pool Layer
Resource Pool (HR Pool)
A named team of staff within a department — e.g. "Trauma Surgical Team". This is a human resource pool. Staff are assigned here via their pool_assignments JSON. Each pool also carries physical pool resources (OR tables, beds) as children.
ResourcePool (HR)
resource_pools
pool_type"human_resource_pool" — always present in every API response. Use this to distinguish from renewable_resource_pool returned by /api/resources/pools.
pool_idHuman-readable unique ID, e.g. TRA-SUR-0001. Referenced in Staff.pool_assignments.
department_idFK → Department.
primary_roleThe clinical role this pool primarily covers. Used as the pool's role label in planning payload.
static_pct / dynamic_pctTarget staff ratio — metadata only, not enforced.
Scheduling: Union-find groups pools by shared staff (via pool_assignments). Demand matrix → shift_requirements[pool_id][alias]. Result stored as pool_centric in Rostering output keyed by pool_id.
Planning: Each pool in the dept generates a resource entry of resource_type:"pool". Staff availability sourced from Rostering.pool_centric[pool_id][date][shift] over the planning horizon.
Auto-trigger: markPlanningDirty is called by createPool, updatePool, updatePoolDemand, createPoolResource, updatePoolResource, and deletePoolResource — planning re-runs within 10 s of any of these. No trigger on pool delete (endpoint does not exist).
Limitations: No DELETE /api/pools/:pool_id endpoint — unused pools accumulate forever. No status field (no soft-delete). Staff → pool link is JSON — orphan refs if a pool is deleted in DB. PoolDemandConfig has no cascade-on-delete (Restrict default), so deleting a pool in DB fails if demand configs exist.
Dept → Pool 1:N Staff ↔ Pool N:N (JSON) Pool → DemandConfig 1:N Pool → PoolResource 1:N (cascade)
↳ PoolDemandConfig
effective_from / toDate range this config is valid. Controller picks the most recent.
demand_matrixJSON: [{shift, mon…sun: headcount}]. Shift names converted to aliases via Shift catalog.
Scheduling: Populates shift_requirements[pool_id] in the scheduling payload. Drives how many staff the solver must assign per shift per day.
Limitation: No cascade-delete with pool — DB will block pool deletion if demand configs exist. Must delete demand configs first.
↳ PoolResource (physical assets in this HR pool)
resource_idUnique ID, e.g. TRA-BED-0001.
statusStored base: AVAILABLE / RESERVED / BLOCKED / MAINTENANCE.
weekly_template{day: {hours: [["HH:mm","HH:mm"]]}}. Availability window sent to planning solver.
block_bookingsRecurring weekly unavailability: [{day, start, end, reason}].
current_stateComputed at read time: ACTIVE reservation → RESERVED; block_booking matches → BLOCKED; else stored status.
Planning: Each PoolResource appears as a member entry in the pool's planning resource block, keyed by resource_id with its weekly_template as availability.
Limitation: Cascade-deleted when the pool is deleted. No independent lifecycle — if you need to decommission a resource, set status MAINTENANCE.
↳ PoolResourceReservation
date / start_time / end_timeSpecific-date booking.
reference_idOptional link to a surgery ID or patient.
statusACTIVE / CANCELLED.
Used in current_state computation. Any ACTIVE reservation covering current UTC time makes the resource appear RESERVED. Managed via /api/pools/:id/resources/:rid/reservations.
L8
Physical Asset Pool Layer
Renewable Resource Pool
Independently managed pools of reusable physical assets — beds, equipment, rooms, devices, vehicles. Distinct from L7 HR pools. Has its own per-unit tracking with status, reservations, and block bookings.
RenewableResourcePool
renewable_resource_pools
pool_type"renewable_resource_pool" — always present in every API response. Use this to distinguish from human_resource_pool returned by /api/pools.
resource_typeBED, EQUIPMENT, ROOM, DEVICE, VEHICLE.
total_capacityExpected total unit count. Used to auto-generate units on create.
statusOPERATIONAL / MAINTENANCE / DECOMMISSIONED.
weekly_templatePool-level open hours per day — operational window.
departmentString only — no FK to Department. Not part of per-dept planning grouping.
Feature: Creating a pool auto-generates total_capacity ResourceUnit rows. Capacity can be increased/decreased via PUT /capacity — decrease only removes AVAILABLE units (rejects if not enough available).
Planning / Scheduling: Not currently projected into either solver payload. Intended for operational inventory tracking and future solver integration.
Auto-trigger: markPlanningDirty fires on: createRenewablePool, addUnitsToPool, updatePoolCapacity, updateWeeklyTemplate, updateUnit, createUnitReservation, updateUnitReservation, deleteUnitReservation, createReservation (pool-level), deleteReservation (pool-level). Planning re-runs within 10 s of any mutation.
Limitations: Department linked by string only — not included in per-department planning grouping. Pool-level reservations is a JSON blob (not normalized), unlike per-unit reservations which are in a proper table.
Pool → ResourceUnit 1:N
↳ ResourceUnit
unit_ide.g. BED-01, VENT-03.
statusStored base: AVAILABLE / IN_USE / MAINTENANCE.
status_tillDateTime — when the current status is expected to expire. Auto-reverts to AVAILABLE if past.
block_bookingsJSON array. Two shapes: {type:"date_range", from, to} or {type:"weekly", day, start, end}.
current_statusComputed at read time: ACTIVE reservation → RESERVED; block_booking match → BLOCKED; status_till expired → AVAILABLE; else stored status.
assigned_to / assigned_atCurrent assignment reference and timestamp.
estimated_releaseWhen unit expected to become available again.
Managed via PATCH /api/resources/units/:unit_id. Accepts status_till and block_bookings updates.
↳ ResourceUnitReservation
from_datetime / to_datetimeSpecific date-time range booking.
reference_idOptional link to a surgery, patient, or workflow.
statusACTIVE / CANCELLED.
CRUD at /api/resources/units/:unit_id/reservations. ACTIVE reservations covering now make the unit appear as RESERVED in current_status. Cascade-deleted with the unit.
L9
Consumable Layer
Non-Renewable Resource
Consumable hospital supplies — blood products, medications, surgical supplies. Tracked by quantity, not individual units. Not part of any solver payload.
NonRenewableResource
non_renewable_resources
categoryBLOOD_PRODUCT, MEDICATION, SUPPLY, etc.
uomUnit of measure: BAG, ML, MG, etc.
stockpile_qtyCurrent stock on hand.
min_required_qtyThreshold below which status becomes SHORTAGE.
statusAVAILABLE / SHORTAGE / OUT_OF_STOCK / MAINTENANCE.
Feature: Inventory tracking for consumables. Status reflects stock level vs minimum required. No child records — quantity-based, not unit-based.
Planning / Scheduling: Not currently projected into either solver payload. Intended for pre-surgery inventory checks and alerts.
Limitations: No depletion tracking (consuming stock doesn't auto-decrement). No department FK — org-level only. No solver integration.
Org → NonRenewable 1:N
L10
Procedure Layer
Surgery
A patient procedure booking belonging to a department. Carries time windows and a stages JSON defining which roles (staff or physical resource) each phase requires. Lifecycle managed by both the server and the planning solver.
Surgery
surgeries
surgery_idServer-generated: SURG-<3-letter prefix>-####. Patient name never sent to solver.
department_idFK → Department. String department auto-derived.
statusLifecycle: DRAFT → ESTIMATED → PLANNING → PLANNED → IN_PROGRESS → DONE | CANCELLED.
time_windowsJSON: {earliest_date, latest_date, planned_start, planned_by}. Bare UTC datetimes.
stagesJSON: five phases (pre_op, operative, post_op, sterilization, recovery) each as array of role requirements.
Planning: Surgeries with eligible status (from SurgeryStatusCatalog to_plan=true) sent to solver grouped by department. Before send: ESTIMATED → PLANNING. On solver completed: PLANNING → PLANNED. Time-based scheduler advances IN_PROGRESS → DONE.
Limitations: Stage assigned is a solver logical token (e.g. "surgeon_1") — not a Staff.staff_id. No back-reference from token to actual staff member. assigned fields referencing IDs not present in the planning payload are stripped before sending to prevent hard solver errors.
Dept → Surgery 1:N StaffTag → stage.role N:N (string)
L11
Output Layer
Rostering Output
Persisted result of a completed scheduling solver run. One row per org per month. Three JSON projections of the same assignment data. Also consumed as staff availability input for the planning solver.
Rostering
rosterings
year / monthTarget calendar month. Composite unique with org_id.
employee_centric{"STAFF-JD-0001": {"2026-08-01": "M"}} — who works what shift each day.
pool_centric{"TRA-SUR-0001": {"2026-08-01": {"M": ["STAFF-JD"]}}} — who's in each pool per shift per day.
date_centric{"2026-08-01": {"TRA-SUR-0001": {"M": ["STAFF-JD"]}}} — per-date view.
statsSolver metrics from the last completed pool group (overwritten, not merged).
Scheduling: Group results are accumulated in memory during the run; after the last group completes, the target month's row is deleted and replaced atomically (deleteMany + create). The current calendar month's row always supplies previous_schedule. Target period depends on trigger: cron/manual → next full calendar month; dirty trigger → today through end of current month.
Planning (cross-pipeline link): Planning preparer reads pool_centric to get each staff member's shift assignments for the planning horizon. This is the bridge from scheduling output to planning input.
Limitations: stats only reflects the last pool group — earlier groups' stats are overwritten. In-memory only until solver responds — server restart loses in-progress data. No per-pool-group granularity in the stored result.
Org → Rostering 1:N Rostering → Planning payload N:1 (read)
L12
Output Layer
Surgery Plan Results
Persisted result of a completed planning solver run. One row per surgery (upserted on each run). Holds the full solver output and is the read endpoint for surgery planning data.
SurgeryPlanResult
surgery_plan_results
surgery_idUnique. Matches the id field returned by the solver in its result[] list (= Surgery.surgery_id string).
organization_idFK to Organisation. Filled from the active org context at planning time.
departmentDepartment name at the time of the run. Denormalised string — no FK to Department.
resultFull solver output for this surgery: { id, resources_assigned, planned_start, … }. Stored as JSON.
created_at / updated_atAuto-managed timestamps. updated_at reflects the last planning run that touched this surgery.
Planning: After Phase 2 (status: "completed"), each entry in result[] is upserted here keyed by surgery_id. If planned_start is present, it is also written back to Surgery.time_windows.planned_start and the surgery status set to PLANNED.
Read endpoints: GET /api/surgery-plans?orgId=<id> — all results for an org, newest first. GET /api/surgery-plans/:surgery_id — single result by surgery_id.
Limitations: One row per surgery — each planning run overwrites the previous result for that surgery. Department is a denormalised string; renaming a department does not update past results. No FK to Surgery — deleting a surgery does not cascade to this table.
Org → SurgeryPlanResult 1:N
