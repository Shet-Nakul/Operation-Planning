Hospital Scheduling System · Solver Reference

Scheduling & Planning Payload Reference

Two independent solver pipelines — staff rostering and surgery planning — that can run concurrently. This document covers how each payload is built, what every field means, and how it flows over WebSocket to the external solver.

● Scheduling

Trigger Conditions

Three independent paths start a rostering run. Only one run can be in flight at a time — isProcessRunning is a server-wide boolean. It is independent of isPlanningRunning — both pipelines may run simultaneously.

1 Manual HTTP trigger POST /api/rostering
Any authenticated caller passes organizationId in the request body. triggerProcess() is called immediately; payload building and WebSocket dispatch happen asynchronously. Returns a processId; poll GET /api/process-state for progress.
2 Daily cron — rosteringScheduler.ts 00:10 UTC daily
Registered with node-cron at server boot via startRosteringScheduler(). Fires at 00:10 UTC every day. Queries all organizations whose GlobalSettings.schedule_date matches today's UTC day-of-month — clamped to the last day for short months (e.g. schedule_date=31 fires on Feb 28). prepareSchedulePayload always targets next calendar month, so firing on day N naturally builds "next month's roster prepared today."
3 Dirty-counter auto-trigger — schedulingAutoTrigger.ts Every 10 s
markSchedulingDirty(orgId) is called from every successful create/update/delete in contractsController, staffController, and poolsController (including updatePoolDemand). A setInterval checks every 10 s — if any org's counter is > 0 and no run is in flight, that org's counter is reset to 0 and triggerProcess(orgId, { triggerDate: new Date() }) is called.

Dirty-trigger payload differs from cron/manual: start_date is set to today (UTC) instead of the first of next month, and horizon is the remaining days in the current month (including today) rather than the full next month. previous_schedule is unchanged — it always reads the current calendar month's Rostering.employee_centric.

Changes that land while a run is active accumulate and are picked up on the next tick after the run completes (via onSchedulingComplete hook).
Post-run cleanup

Group results are accumulated in memory (accEmployeeCentric, accPoolCentric, accDateCentric) as each completed message arrives. Only after the last group completes does the manager save to the database in two steps:

  1. Delete the previous result — removes the single existing row for this org + year + month (if any). Prisma's deleteMany is used here simply because it accepts plain field filters; it still only ever removes that one row since (organization_id, year, month) is a unique key.
  2. Write the new result — inserts a fresh row with the fully accumulated data from all groups.

This means the old rostering data stays readable throughout the run and is replaced in one clean operation at the very end.

● Scheduling

Union-Find Grouping

Pools that share at least one employee are merged into a single solver job. Each group produces one payload sent serially to the solver. The solver enforces rest constraints across all pools an employee appears in — it needs the full picture at once.

Algorithm (schedulingPayloadPreparer.ts)Logic
// 1. For each ResourcePool, collect the set of Staff who have that pool_id
//    in their pool_assignments JSON array.
poolEmployeeSets["TRA-SUR-0001"] = new Set(["STAFF-JD-0001", "STAFF-AL-0002"])
poolEmployeeSets["TRA-ICU-0001"] = new Set(["STAFF-AL-0002", "STAFF-SM-0003"])
poolEmployeeSets["CARD-SUR-0001"] = new Set(["STAFF-RS-0004", "STAFF-MK-0005"])

// 2. Union-find: pair each pool against every other pool.
//    If any employee appears in both → union(poolA, poolB).
// STAFF-AL-0002 is in both TRA-SUR-0001 and TRA-ICU-0001 → merged into Group A
// CARD-SUR-0001 has no overlap → separate Group B

// Result:
Group A → pools ["TRA-SUR-0001", "TRA-ICU-0001"]  → 1 payload
Group B → pools ["CARD-SUR-0001"]                → 1 payload
Skip condition

If a group contains fewer than 2 employees on a DYNAMIC contract, no payload is built for it. The check runs after union-find, per group. Static-only groups have nothing for the solver to optimize and are silently dropped.

Field Breakdown

FieldSourceLogic
start_dateComputedCron / manual: First day of next calendar month in UTC — new Date(UTC(year, month+1, 1)).
Dirty trigger: Today's UTC date — new Date(UTC(year, month, day)).
horizonComputedCron / manual: Day count in next month (28–31), derived as day 0 of month+2.
Dirty trigger: Remaining days in the current month including today — lastDayOfMonth − today.getUTCDate() + 1.

employee_profiles[id].poolsStaff.pool_assignmentsFiltered to only pool IDs in this group. An employee in pools across two groups contributes only the relevant IDs here.
employee_profiles[id].weekly_templateStaff.weekly_templatestatic only Role-based shape: {day: [{start, end, role}]}. Empty array = off. Only included when the employee is on a STATIC contract AND the field is non-empty.
contracts[id]Contract + ForbiddenPatterndynamic Array of constraint objects built from schedulingRules (name→snake_case, mode→hard) + assignmentLimits (adds value) + global ForbiddenPattern.forbidden_patterns entries that have a pattern field. static Always null. All org contracts included, not just the group's.
shift_requirements[pool_id][alias]PoolDemandConfig.demand_matrixShift name converted to alias via org Shift catalog (shiftNameToAliasMap). Falls back to shift name if no alias. Pools with no employees in the group or no demand config are omitted.

● Scheduling

WebSocket Flow

The payload is wrapped in a {data, config} envelope before being sent. Groups are dispatched serially — one group at a time.

Full WS message (JSON.stringify)JSON
{
  "data": { /* payload above */ },

  "config": {                        // hardcoded in schedulingProcessManager.ts
    "initialization": { "strategy": "random" },
    "search": {
      "max_iterations": 100000,
      "max_minutes": 5,           // solver hard stop
      "tabu_tenure": 500,
      "restart_strategy": "adaptive_sigmoid",
      "initial_temp": 50.0, "min_temp": 0.05, "annealing_duration": 500
    },
    "moves": { "n_samples": 3, "max_operations": 9, "max_block_size": 35 },
    "logging": { "log_interval": 500, "print_interval": 5000 }
  }
}
Connect to WEBSOCKET_URL_ROSTER
Single persistent connection. On open, calls sendNext() for group index 0.
Send JSON.stringify({data, config}) → start 60 s timeout
If no response within 60 s, fails the entire run.
status: "progress" → log & keep waiting
Clears and resets the timeout. Logs data.progress_pct.
status: "completed" → merge DB, send next group
Extracts year/month from first date key in employee_centric (fallback: pool_centric → date_centric). Upserts Rostering row. Increments group index, calls sendNext(). If last group: closes connection.
status: "error" → fail run
Marks process failed, closes connection, rejects promise. isProcessRunning reset via close handler.
Unexpected close → reconnect (max 5, 500 ms delay)
Retries connect(). After 5 failures, fails the run.
All groups done → completion hook → isProcessRunning = false
Fires schedulingCompletionHook(orgId, success) registered by schedulingAutoTrigger.ts. Hook resets dirty counter, checks for follow-up runs.
● Scheduling

Result & Storage

ColumnMerge strategy
employee_centricObject.assign(existing, new) — overwrites per-staff_id. Employees in different groups can't collide.
pool_centricObject.assign(existing, new) — overwrites per-pool_id. Pools are always in exactly one group.
date_centricPer-date: Object.assign(existing[date], new[date]) — pools from group A and group B both write their keys without clobbering each other.
statsOverwritten by the last group's response (no merge).
No stale carry-over

The target month's row is deleted before any group is sent. First group uses the create branch of upsert. Subsequent groups in the same run use update + merge. Results are available via GET /api/rosterings?view=latest|employee|pool|date.

● Planning

Trigger Conditions

Two paths start a surgery planning run. isPlanningRunning is independent of isProcessRunning — planning and scheduling can run at the same time. isPlanningRunning is set synchronously before the first await to prevent two near-simultaneous callers from both passing the check.

1 Manual HTTP trigger POST /api/planning
Authenticated caller triggers immediately. Returns a processId; poll GET /api/planning-state for progress. Unlike rostering, there is no cron path — planning is event-driven only.
2 Dirty-counter auto-trigger — planningAutoTrigger.ts Every 10 s
markPlanningDirty(orgId) is called from every successful create/update/delete in surgeriesController, poolsController, staffController, and from globalSettingsController's upsert. A setInterval checks every 10 s — if any org's counter is > 0 and no run is in flight, that org's counter is reset to 0 and triggerSurgeryPlanning() is called. Changes that land mid-run accumulate and are picked up on the next tick after onPlanningComplete fires.
Surgery status promotion — before sending

After prepareSurgeryPlanningPayloads() returns, any surgery in the payloads that is still in ESTIMATED status is promoted to PLANNING via prisma.surgery.updateMany. Only ESTIMATED surgeries are promoted — PLANNING and PLANNED ones are left alone.

● Planning

Per-Department Grouping

One payload is built per department. The solver sees each department's full resource picture in isolation — pool-based staff, individually-listed surgeons, and physical pool resources (OR tables, beds).

Resource typeCondition for inclusion
Pool-based staff (resource_type: "pool")The ResourcePool.department_id matches the department. Availability comes from the already-solved staff roster (Rostering.pool_centric) over horizon×2+1 days.
Individual staff (resource_type: "individual")Staff with department_id matching the dept, on a STATIC contract, with no pool assignments, AND whose primary role (from weekly_template) slug-matches a surgery stage role that has a non-null assigned token. The assigned value is a solver logical token like "surgeon_1", not a Staff.staff_id.
Physical pool resources (resource_type: "pool")Each ResourcePool in the dept that has at least one PoolResource child. Availability comes from each PoolResource.weekly_template.
Skip condition

A department with no pools, no eligible individual staff, and no eligible surgeries is skipped — no payload is produced for it. Eligible surgeries are those whose status is in the SurgeryStatusCatalog where to_plan=true. If the catalog is empty, defaults to the set {ESTIMATED, PLANNING, PLANNED}.

Surgery eligibility — status filter

Surgeries with status DRAFT, IN_PROGRESS, DONE, or CANCELLED are excluded from the payload (via isExcludedFromPlanning()). The SurgeryStatusCatalog table per-org can override this: any status with to_plan=true is included regardless.

● Planning

WebSocket Flow

Payload sent directly — no {data, config} wrapper. Otherwise mirrors the scheduling flow: serial dispatch, 60 s timeout, 5 reconnects at 500 ms.

Key difference from scheduling

The planning WebSocket sends ws.send(JSON.stringify(item)) — the payload object directly. The scheduling WebSocket sends JSON.stringify({data: item, config: {...}}). Different solver endpoints, different message contracts.

Connect to WEBSOCKET_URL_PLANNING
On open, calls sendNext() for department index 0.
Send raw JSON.stringify(payload) → start 60 s timeout
No config wrapper. Timeout rejects on expiry.
status: "progress" → log & keep waiting
Logs data.progress_pct. Does not affect surgery status.
status: "completed" → promote surgeries, send next dept

Result & Side Effects

EventSide effect
Payload built (before sending)All ESTIMATED surgeries in the payloads → PLANNING via bulk updateMany
Solver returns completed for a deptAll PLANNING surgeries in that dept → PLANNED via bulk updateMany. Result data is logged but not stored to a DB table (no SurgeryPlanning model yet).
Solver returns errorisPlanningRunning = false. Surgeries remain in PLANNING status — no rollback. Subsequent runs will re-include them (since PLANNING is in the to_plan set by default).
Poll stateGET /api/planning-state — in-memory only, resets on server restart
Surgery lifecycle summary

DRAFT (created) → ESTIMATED (manual PUT) → PLANNING (auto, payload built) → PLANNED (auto, solver completed). CANCELLED can be set manually at any stage. Once PLANNED, PUT time_windows.planned_start with a non-null value keeps status PLANNED (auto-promotion only applies when transitioning to PLANNED). The SurgeryLifecycleScheduler then handles IN_PROGRESS and DONE via time-based background ticks.
